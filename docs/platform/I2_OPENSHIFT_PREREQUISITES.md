# I2 — OpenShift / CRC Prerequisites

## Target

Local architecture validation on **OpenShift Local / CRC** with a later enterprise mapping to Red Hat OpenShift Container Platform self-managed.

## Mandatory client tools

Record actual versions before execution:

```bash
crc version
oc version
kubectl version --client
helm version
git --version
```

Recommended additional tools:

```bash
jq --version
yq --version
curl --version
openssl version
```

## Cluster preflight

```bash
crc status
oc whoami
oc get clusterversion
oc get nodes -o wide
oc get storageclass
oc get route -A | head
oc api-resources >/dev/null
```

Expected for the local lab:

- CRC started and API reachable ;
- user can create a project/namespace ;
- dynamic storage class available or storage approach documented ;
- enough CPU/RAM/disk for Pega + database + selected backing services ;
- cluster DNS and Route ingress functional ;
- no claim of multi-worker HA from CRC.

## Resource capacity gate

Pega and backing services can be resource intensive. The repo deliberately does not invent a universally safe CRC size.

Before deployment capture:

```bash
oc describe node
oc adm top nodes 2>/dev/null || true
oc get pvc -A
```

Then compare available capacity with the requests/limits generated by the selected Pega Helm values. If capacity is insufficient, stop rather than disabling safeguards blindly.

## Namespace

Default lab namespace:

```text
mayabank-pega
```

The namespace is created from versioned manifests and receives labels identifying environment and data classification.

## Registry prerequisites

Pega runtime/install images are proprietary/entitlement-controlled. Runtime gate:

1. user confirms authorized image access ;
2. user chooses a registry reachable from CRC ;
3. image tags/digests are recorded without credentials ;
4. image pull secret is created locally in OpenShift ;
5. secret value is never committed.

Example local action:

```bash
oc -n mayabank-pega create secret docker-registry pega-registry \
  --docker-server="$PEGA_REGISTRY" \
  --docker-username="$PEGA_REGISTRY_USER" \
  --docker-password="$PEGA_REGISTRY_PASSWORD"
```

## Database prerequisites

Before Pega installation:

- confirm DB engine/version support for selected Pega patch ;
- confirm JDBC driver/version ;
- create DB/user using local secrets ;
- validate DNS/network connectivity from namespace ;
- distinguish empty database from **Pega schema installed** database ;
- capture backup/restore approach.

A PostgreSQL lab manifest may be used for architecture exercises, but it is not automatically declared supported until the selected Pega support matrix has been checked.

## DNS / Routes / TLS

CRC provides an apps domain. Record it:

```bash
oc get ingresses.config/cluster -o jsonpath='{.spec.domain}{"\n"}'
```

TLS strategy:

- route edge/re-encrypt/passthrough according to chosen Pega chart configuration ;
- use a generated lab certificate only for local non-production testing ;
- never commit private keys ;
- enterprise target uses organization certificate management.

## Network policy

The lab must document/limit these flows:

```text
Ingress Router -> Pega web
Pega -> PostgreSQL
Pega -> DNS
Pega -> approved external APIs/registry only as required
Integration adapters -> Pega/API/core mocks
Observability agents/collectors -> monitored workloads
```

CRC platform namespaces are not modified blindly to satisfy an application policy.

## Storage

Capture default StorageClass and use PVCs for stateful lab components. Do not assume ReadWriteMany. Search/reporting services may have their own storage requirements.

## Security prerequisites

- no `anyuid`/privileged SCC grant by default ;
- no blanket cluster-admin service account ;
- secrets not stored in Git ;
- least privilege namespace RBAC ;
- NetworkPolicy present where compatible ;
- image provenance recorded ;
- no real customer data.

If an official Pega image requires a specific OpenShift SCC/security-context accommodation, record the exact requirement from the version-specific documentation before changing security posture.

## Helm prerequisites

```bash
helm repo add pega https://pegasystems.github.io/pega-helm-charts
helm repo update
helm search repo pega
helm show values pega/pega > /tmp/pega-values.txt
```

Do not run install until values are reviewed and entitlement gate passes.

## Evidence directory

Runtime scripts will write non-secret evidence under:

```text
evidence/runtime/
```

Expected outputs: versions, nodes, storage classes, Helm chart version, pod status, routes, events, smoke tests.
